## 2. 产品愿景与目标

### 2.1 用户最初目标（产品愿景）

1. **核心产品**：做一款**漏扫工具**，能够对代码/项目进行安全漏洞扫描。  
2. **进阶目标**：在核心能力之上，做**IDE 插件**，实现：  
   - **实时检测**：在写代码过程中实时发现安全隐患；  
   - **问题标注**：在编辑器中标注存在风险的代码位置；  
   - **危险等级**：对每个问题标注严重程度（如 Critical / High / Medium / Low）；  
   - **修改建议**：由 **AI 生成**针对当前代码的修复建议。  

即：**漏扫工具 + IDE 内实时安全检测 + 危险等级 + AI 修复建议**。

### 2.2 产品目标归纳

| 维度 | 目标描述 |
|------|----------|
| **核心能力** | 对项目/单文件进行 SAST 扫描，输出漏洞列表及严重等级。 |
| **使用形态** | ① 独立漏扫（CLI/CI）；② IDE 内实时检测（插件）。 |
| **体验要求** | 编辑时即可看到行内诊断、等级与说明。 |
| **智能化** | 修复建议由 AI 生成，结合代码上下文与知识库。 |

### 3.1.1 当前能力分级

| 状态 | 能力 |

### 3.2 与愿景的差距

1. **跨文件能力尚未达到默认可承诺级别**
   - 当前：工作区依赖图已构建，单文件诊断链路稳定；跨文件结果仍保留实验性入口。
   - 期望：补齐默认关闭 / 能力边界 / 回归基准三件事后，再提升为正式能力。

2. **实时性**  
   - 当前：didOpen / didSave / didChange 防抖扫描、增量缓存、复扫确认均已接入。
   - 可选增强：输入防抖后增量分析，平衡体验与性能。  

3. **检测深度与误报**  
   - 污点与规则已大幅优化，但在复杂数据流、跨文件、多语言上仍有提升空间；需持续用基准（如 NodeGoat/自建用例）做 Recall/Precision 监控。  

### 3.3 评估结论

- **漏扫 + IDE 插件 + 危险等级** 已形成闭环，与「做漏扫 + IDE 内实时标注与等级」的目标**基本对齐**。  
- **AI 修改建议** 已完成 IDE 集成，但用户信任仍取决于：安装链路统一、扫描状态可解释、baseline/注释/修复动作的边界明确。

## 4. 产品定位与范围

### 4.1 产品定位

**Aegis AI** 是一款面向开发流程的**智能代码安全审计产品**，包含：

- **独立漏扫**：适用于 CI/CD、定期扫描、报告审计。  
- **IDE 内实时防护**：写代码时即时发现隐患并标注等级，未来提供 AI 驱动的修复建议与一键修复。  

### 4.2 系统边界

- **在范围内**：  
  - 静态分析（AST + 规则 + 污点）；  
  - 漏扫 CLI/CI、报告生成；
  - LSP Server + VS Code/Cursor 扩展；  
  - RAG 知识库与 AI 增强（修复建议、验证）；  
  - 漏洞类型：SQL/NoSQL 注入、XSS、RCE、路径穿越、硬编码凭证、反序列化等。  

- **不在范围内（当前版本）**：  
  - 动态分析、IAST、DAST；  
  - 二进制/固件分析；  
  - 非 LSP 的独立 JetBrains 原生插件（可后续通过 LSP 适配）。  

### 4.3 用户角色

| 角色 | 主要场景 |
|------|----------|
| 开发者 | 在 IDE 中写代码时查看实时诊断、等级与修复建议。 |
| 安全/DevOps | 使用 CLI 或 GitHub Actions 做全量/增量扫描，查看 HTML/JSON/SARIF 报告。 |
|  CI/CD | 流水线中集成扫描，卡点或报告上传（如 SARIF）。 |

### 4.4 已知局限与演进方向

本文档作为**商业产品设计**时，当前方案的核心竞争力边界如下；不回避、并在后续迭代中补齐。

- **扫描粒度**：当前以**单文件**为主，跨文件依赖图已建但尚未全面用于污点传播；通过**内联 (6.6.2)** 覆盖大部分跨函数场景，全量过程间分析为后续演进。  
- **内联与坐标**：内联会引入**虚拟行号**，必须实现**坐标回溯 (6.6.2.1)**：虚拟节点 → (CallSite, DefinitionSite) 映射，否则 IDE 高亮与报告位置错误。  
- **分析深度**：**别名分析**尚未实现，仅赋值建边；复杂引用与对象传播为已知短板。  
- **性能**：Python 主线程内跑重分析会卡顿；须通过**多进程/后台守护 (9.1.1)** 或核心引擎迁移至 Go/Rust 缓解。  
- **AI 体验**：仅版本校验会导致「用户手不停则建议永远作废」；须引入 **OT / Fuzzy Patching (7.3.1)** 使建议在编辑后仍可应用。  
- **Parser**：AST 解析失败率是核心 KPI；须满足 **Parser 兼容性测试标准 (10.1.1)**，降级仅作偶发容错。

## 6. 核心模块设计

### 6.1 分析引擎（analysis）

| 模块 | 路径/代表类 | 职责 |
|------|-------------|------|
| 规则引擎 | `rule_engine` | 按语言分发到 JS/Python 分析器，汇总 Finding 列表。 |
| 语言分析器 | `javascript_analyzer`, `python_analyzer` | 构建 AST、执行规则、挂接污点与数据流。 |
| 规则集 | `rules/sql_injection`, `nosql_injection`, `xss`, … | 每类漏洞的 AST/正则规则与 Source/Sink/Sanitizer 使用。 |
| 污点分析 | `taint/taint_analyzer`, `taint_graph`, `source_sink_registry` | 构建污点图、路径查询、供规则层调用。详见 **6.6 污点分析实现逻辑**。 |
| 跨文件分析 | `cross_file_analyzer` | 解析 require/import，构建项目依赖图，为后续跨文件污点铺路。 |
| 分析上下文 | `analysis_context`, `file_context`, `dataflow_tracker` | 单文件/多文件上下文与变量污点状态。 |

### 6.6 污点分析实现逻辑（核心算法与难点）

本节说明「构建污点图」背后的实现逻辑，避免仅用名词带过。污点分析是本项目的核心难点，实现上涉及数据流、上下文与终止性。

#### 6.6.1 污点传播算法定位

- **方法论**：采用**基于数据流分析（Data Flow Analysis）**的污点追踪，而非简单词法/正则匹配。  
- **流程**：  
  1. **建图阶段**：遍历 AST，收集赋值（含解构、Express 路由回调中的 `req`）、识别 Source/Sink（通过 `SourceSinkRegistry`），在 `TaintGraph` 中建立节点（TaintNode）与边（TaintEdge，类型包括 ASSIGNMENT、PROPAGATION、PARAMETER_PASS、RETURN 等）。  
  2. **路径查询阶段**：从所有 Source 节点出发，沿边做 **BFS**，找到能到达 Sink 的路径（`find_paths_to_sinks()`），生成 TaintPath。  
- **与规则层的关系**：规则层（如 NoSQL/SQL/XSS 规则）在检测到潜在 Sink 时，通过 `context.taint_graph` 查询 `is_var_tainted`、`get_taint_source_info` 等，以决定是否上报及严重程度；污点图是「先建图、后查询」的单向依赖。

#### 6.6.2 函数调用与上下文切换：从「不进入被调函数」到「内联」策略

- **现状与商业现实**：  
  - 当前设计明确约定：函数调用时**不进入被调函数**，仅过程内传播 + Express 路由回调特例。  
  - 真实项目中**约 90% 的漏洞跨越函数调用**（例如 `main()` 中 `let payload = getUserInput(); unsafe(payload);`，`unsafe(input)` 内 `eval(input)`）。若不跨函数追踪，扫描器只能在「调用处断了」，只能扫到类似 `eval(req.query.id)` 这种单行式代码，与市面免费 ESLint 插件能力重叠，缺乏商业说服力。  
  - 因此：**必须**在文档与实现中走出「玩具级」单过程分析，引入可落地的跨函数能力。

- **策略选择：放弃全量过程间，采用内联 (Inlining)**  
  - **不做**：全量过程间分析（完整调用图 + 过程间摘要），实现与维护成本极高，易失控。  
  - **必须做**：**内联 (Inlining) 策略**——对**简单、短小、同文件内的私有/局部函数**，在构建污点图时将其**虚拟展开**到调用处：  
    - 在 AST 或中间表示层面，遇到满足条件的函数调用（如函数体行数/节点数低于阈值、无递归、无复杂控制流）时，将被调函数体「内联」到调用点，再在展开后的逻辑上跑现有过程内污点分析。  
    - 这样 **Source → 调用 A → 调用 B → Sink** 中，若 A/B 均为可内联的小函数，则等价于单次过程内分析，能覆盖**约 80% 的跨函数漏报**，以较低成本让工具从「玩具」升级为「正经扫描器」。  
  - **实现约束**：需在 TDD 与代码中明确「可内联」的判定条件（如最大行数、最大节点数、是否同文件、是否递归）、内联深度上限（避免爆炸），以及内联后的污点建图与现有 TaintGraph 的衔接方式。

- **仍不覆盖**：  
  - 跨文件调用、大型/递归/动态调用、回调与异步中「从被调函数返回再传入下一层」的复杂链，仍依赖后续的过程间/调用图演进。  
  - **设计结论**：函数调用时的「上下文切换」**通过内联有限地进入被调函数**，不维护完整调用栈；全量过程间分析仍为后续演进项。

#### 6.6.2.1 内联带来的「坐标地狱」与坐标回溯（Source Map）

- **问题**：内联会把被调函数（如 `funcA` 定义在第 50 行）**虚拟展开**到调用处（第 10 行）。分析器在**展开后的 AST** 上发现漏洞时，若直接使用「展开后的虚拟行号」上报：  
  - **报第 10 行**：用户看到的是函数调用，无法理解漏洞具体在哪段逻辑。  
  - **报第 50 行**：用户会懵，因为漏洞是「第 10 行传入的参数 + 第 50 行逻辑」共同触发的，单报 50 行缺少调用上下文。  
  若没有从「虚拟节点」回溯到「原始源码位置」的机制，IDE 高亮与报告位置会错乱或难以理解。

- **缺失的设计**：文档与实现中**必须**包含 **AST 变形后的坐标回溯机制**。  
  - **映射表**：在内联时维护 **虚拟节点 → 原始节点** 的映射，至少记录：  
    - **CallSite**：调用点（如第 10 行 `funcA(...)`）  
    - **DefinitionSite**：被内联函数的定义位置（如第 50 行函数体）  
  - **上报策略**（须与 LSP 一致）：  
  - **主位置 (Primary)**：**必须**为 **CallSite**（用户正在「传入脏数据」的那一行），这样波浪线画在用户当前关注处；若主位置报在 DefinitionSite，用户会困惑「我没动那个函数」。  
  - **关联位置 (Related)**：将 **DefinitionSite**（如 Sink 所在行）放入 Finding 的 **related_locations**，并设 `message` 如 `SINK: Execution of eval() happens here`，由 LSP 层映射为 `Diagnostic.relatedInformation`（见 7.1、7.2）；用户悬停时可点击跳转到定义处。  
  - 不得仅在 details 里写「Line 11 calls Line 6」等纯文本，否则无法点击跳转、体验极差。  
- **小结**：内联实现必须伴随 **Virtual Node → (CallSite, DefinitionSite)** 的映射表与回溯逻辑；Finding 必须支持 **related_locations**，且 LSP 转换层必须将其映射为 **Diagnostic.relatedInformation**，否则多位置无法合规展示。

#### 6.6.3 循环与终止性

- **图遍历防死循环**：路径搜索使用 **visited 集合**（BFS 中已访问节点不再入队），避免在污点图上因环导致无限循环。因此「建图 + BFS」阶段是终止的。  
- **循环结构对污点的影响**：  
  - 当前**未**做迭代不动点分析（如 while 内多次赋值直到不动点）。  
  - 依赖「一次 AST 遍历」收集到的赋值与边；若循环体内某变量被多次赋值，仅最后一次赋值会覆盖 `_variables` 中的映射，可能漏掉中间状态。  
  - 对「循环导致污点反复传播」的完整处理（如 Kildall 风格迭代）列为后续增强项。

#### 6.6.4 别名分析（Aliasing Analysis）的缺失

- **问题**：当前仅有「赋值建边」（如 `x = source` → `x` 污染），**未**处理**别名/引用**关系。  
  - 例如：`let a = b;` 若 `b` 已被污染，`a` 是否算污染？若仅按赋值建边且 `b` 已在变量表中标记为污点，则 `a` 可通过本次赋值继承污点；但若涉及**对象引用、数组元素、闭包捕获**等（如 `obj.x = tainted; later(obj.x)`），当前模型只有「赋值建边」，没有显式的别名集（alias set）或指向分析，无法刻画「多个名字指向同一内存」的复杂情况。  
- **商业现实**：在商业 SAST 中，**别名分析是核心壁垒**之一；缺少则漏报与误报都会上升。  
- **设计结论**：本文档**明确将别名分析列为当前缺失**；实现上可先依赖「赋值传播 + 简单变量表」覆盖大部分单变量场景，后续再引入别名集或轻量指向分析，并在 TDD 中单独小节描述目标与约束。

#### 6.6.5 小结

| 问题 | 当前设计/实现 |
|------|----------------|
| 污点传播算法是什么？ | 数据流分析：AST 建图（节点+边）+ BFS 路径查询；非词法匹配。 |
| 函数调用时上下文怎么切换？ | 过程内传播 + Express 路由特例；**必须**实现**内联 (Inlining)** 覆盖简单跨函数调用。 |
| 循环如何避免死循环？ | 图遍历用 visited 保证终止；循环内污点不做迭代不动点。 |
| 别名（如 a=b，b 污染则 a？） | **未**做显式别名分析；仅赋值建边，复杂引用列为缺失与后续演进。 |

#### 6.4.1 AI 工程与约束（避免“想当然”）

以下为 AI 能力落地时必须明确的设计与风险，而非乐观假设。

**（1）发送给 LLM 的代码范围与 Token**

- **范围策略**：建议采用「漏洞相关上下文」而非整文件默认全发。可选策略：  
  - 仅发送**漏洞行及前后 N 行**（如 ±10 行）作为上下文，减少 Token 与噪音。  
  - 或按「函数/块」边界截取（包含该 Finding 所在函数体）。  
- **Token 超限**：  
  - 单次请求前估算 Token（按模型上限，如 4K/8K），超出则**截断**。  
  - **截断策略**须在 TDD 中约定：例如保留「漏洞行 + 其所在函数/块」，丢弃文件首尾；或按行从漏洞行向两侧扩展直到达到上限。  
  - 实现上需配置 `max_context_lines` 或 `max_tokens_for_code`，并在日志中记录截断发生，便于排查。

**（2）源码隐私与合规**

- **风险**：将商业/客户源码直接发送至外部 LLM API（如 DeepSeek），存在**源码泄露与合规风险**；仅保护 API Key 不足以解决该问题。  
- **设计约束**：  
  - **默认**：在未明确用户同意或未采用下述方案时，**不将完整源码发送至外部 API**；AI 增强应为显式可选（如用户勾选「使用在线 AI 建议」并知晓风险）。  
  - **可选方案**：  
    - **本地/私有化部署**：使用本地或企业内网可用的 LLM（本地模型、私有化 API），源码不出域。  
    - **最小上下文**：仅发送漏洞类型 + 行号 + 极短片段（如单行或脱敏后的片段），不发送完整文件或项目结构。  
    - **合规说明**：在文档与 UI 中明确告知「使用云端 AI 会将代码片段发送至第三方」，需用户确认。  
- 本文档在安全章节（9.2）中同时要求：**禁止将未脱敏的完整源码写入日志或发送至不可信端点**；AI 调用需纳入该策略。

**（3）从 LLM 自然语言到 IDE 可用的修复（结构化输出）**

- **问题**：LLM 返回的是自然语言，IDE 插件需要 **TextEdit**（或 LSP 的 `TextDocumentEdit`）才能精准替换代码；若仅靠正则从自然语言里“抠”代码，在生产环境中脆弱且易出 Bug。  
- **设计方向**：  
  - **优先**：要求 LLM **结构化输出**（如 JSON），字段至少包含：`replacement_text`、可选 `range`（start_line/end_line 或 start/end offset），由服务端或 LSP 直接转为 LSP `TextEdit`，再通过 Code Action 应用。  
  - **Prompt 约束**：在 Prompt 中明确要求「只输出指定 JSON 格式，不要额外解释」，并可选用模型支持的 JSON mode / 结构化输出能力。  
  - **降级**：若无法使用结构化输出，则仅将 LLM 结果作为**说明文本**展示给用户（如 Hover/Code Action 的 description），**不自动应用**为编辑，避免错误替换。  
- **测试**：对「LLM 返回 → TextEdit」的解析逻辑必须有单测与异常分支（非法 JSON、缺失字段、越界 range 等）。

### 6.5 数据流（扫描链路）

```
输入(文件/项目)
  → 语言识别 → 规则引擎(analyze_*)
  → [可选] 污点分析(TaintAnalyzer) / 跨文件(CrossFileAnalyzer)
  → 规则执行 → 生成 Finding 列表
  → [可选] RAG 增强 / AI 分析 → 附加建议与元数据
  → 输出：LSP Diagnostic 或 报告文件(HTML/JSON/SARIF)
```

## 7. 接口与数据契约

### 7.1 Finding（单条漏洞结果）

Finding 既用于**报告展示**，也用于**程序消费**（如 LSP Diagnostic、Code Action）。因此必须同时满足人类可读与机器可精确定位。

#### 7.1.1 字段定义（含 IDE 所需的精确定位）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| type | string | 是 | 漏洞类型，如 SQL_INJECTION, NOSQL_INJECTION, XSS。 |
| severity | string | 是 | Critical / High / Medium / Low / Info。 |
| line | int | 是 | 主行号（从 1 开始），兼容旧报告与简单展示。 |
| **start_line** | int | 推荐 | 起始行（1-based），用于精确高亮。 |
| **start_character** | int | 推荐 | 起始列（0-based）。 |
| **end_line** | int | 推荐 | 结束行（1-based）。 |
| **end_character** | int | 推荐 | 结束列（0-based）。 |
| file | string | 是 | 文件路径。 |
| details | string | 是 | 描述信息。 |
| message | string | 否 | 短摘要。 |
| suggestion / fix | string | 否 | 修复建议（RAG/AI 填充）。 |
| **related_locations** | List[Location] | 否 | 关联位置列表，用于内联/跨函数等「主位置 + 关联位置」场景；**必须**映射为 LSP 的 `Diagnostic.relatedInformation`，见 7.2。 |

- **Location 结构**（用于 `related_locations` 及 LSP 映射）：  
  - `file_path`: string，文件路径。  
  - `start_line` / `end_line`: int（1-based）；可选 `start_character` / `end_character`（0-based）用于字符级高亮。  
  - `message`: string，该关联位置的说明（如 `SINK: Execution of eval() happens here`），供 LSP 悬停与跳转展示。  

- **精确定位**：IDE 插件需要**字符级 range** 才能做行内高亮与 Code Action 的 TextEdit。仅 `line` 无法区分同一行多处问题，且无法正确高亮跨行片段。规则引擎/分析器在产出 Finding 时，应尽量填充 `start_line`、`start_character`、`end_line`、`end_character`（可从 AST 节点 `start_point`/`end_point` 得到）。若缺失，则 LSP 层用 `line` 退化为「整行」（character 0 到行末或 999）。

#### 7.1.2 报告用与程序用的统一

- 报告生成器：可仅展示 `line` 或 `start_line`~`end_line`。  
- LSP/IDE：**必须**使用 range（由 Finding 的 start/end 或 line 退化得到）发布 Diagnostic 与 Code Action，保证高亮与编辑位置正确。

### 7.2 LSP Diagnostic 与 Finding 映射

- **range**（主诊断位置）：  
  - 若 Finding 含 `start_line`/`start_character`/`end_line`/`end_character`，则转为 LSP 的 0-based `Range`（Position 为 line-1, character）。  
  - 若缺失，则退化为 `line` 对应行、character 0 到 999（或当前行长度）。  
  - **内联场景**：主诊断**必须**锚定在 **CallSite**（用户「传入脏数据」的调用处），而非 DefinitionSite；否则用户在第 11 行写代码却看到第 6 行报错会困惑，或只看到第 11 行的 `unsafe(payload)` 而无 `eval` 会误以为误报。见 6.6.2.1。  
- `severity`：Critical/High → Error；Medium → Warning；Low → Information；Info → Hint。  
- `source`: `"Aegis AI"`。  
- `code`: Finding.type。  
- `message`: Finding.details 或 message。  
- **relatedInformation**（强制）：  
  - Finding 的 **related_locations** **必须**映射为 LSP 的 `Diagnostic.relatedInformation`（`DiagnosticRelatedInformation[]`），不得自行发明「两处一起高亮」或仅在 message 里写「Line 11 calls Line 6」等不可点击的文本。  
  - 每条 `Location` 转为 `DiagnosticRelatedInformation`：`location` = 对应文件的 `Range`（0-based），`message` = 该条的 `message`。  
  - **效果**：VS Code 在主位置（如 CallSite）画波浪线，悬停时列出关联位置（如 DefinitionSite）的链接，用户点击即可跳转；否则多位置无法可点击展示，体验不可接受。  

### 7.3 LSP 与文档状态同步（避免“脏数据”）

当用户在扫描过程中修改了文档，行号或内容会变化，若仍用旧结果发布 Diagnostic，会产生错位或“脏数据”。须在设计中明确同步策略。

- **文档版本**：LSP 协议中 `TextDocumentItem` 含 `version`。每次 didOpen/didChange/didSave 都会带来新 version。  
- **绑定规则**：  
  - 每次发起扫描时**记录当前文档 version**（如 `scan_version`）。  
  - 在**发布 Diagnostic 之前**，再次读取当前文档 version；若 `current_version != scan_version`，表示文档已被用户修改，**本次扫描结果作废**，可选择：  
    - **不发布**（丢弃本次结果），或  
    - **重新排队扫描**（基于最新内容再扫一次），并仅在新扫描完成后发布与新 version 绑定的 Diagnostic。  
- **实现要点**：  
  - 异步扫描时，在回调里必须做 version 校验再 `publish_diagnostics`。  
  - 若使用 didChange + debounce，debounce 触发时以**最新 version** 为准，旧 timer 触发时若 version 已变则直接 return，不发布。  
- **小结**：TDD 要求 LSP Server 在发布 Diagnostic 前**校验文档版本**，避免编辑后行号变化导致的错位与脏数据。

#### 7.3.1 AI 修复的「同步」黑洞（版本校验不足）

- **问题**：上述「版本不对则作废」策略对**普通 Diagnostic** 足够，但对 **AI 生成的修复建议** 严重不足。  
  - **情景一**：LLM 建议修改「第 10 行」；用户在等待 AI 响应的数秒内**删除了第 5 行**，则当前文档中「第 10 行」已变为原来的第 9 行，若仍按行号应用 `replacement_text`，会改错位置甚至破坏代码。  
  - **情景二**：若策略仅为「版本号不对就作废」，则只要用户**持续编辑**，AI 建议会**永远被作废**、永远弹不出来，功能形同虚设。  
- **设计方向**：**不仅是校验版本，更需引入同步/合并能力**：  
  - **远期**：OT (Operational Transformation) 或通用 Fuzzy Patching——基于当前文档与请求时文档的 Diff，将 AI 的 `replacement_text`/`range` 映射到当前版本。  
  - **危机**：「模糊匹配」的实现难度易被低估：若用户不仅改了行号还改了**变量名**，或把一段代码**重构到另一文件**，则已超出「基于 Diff 的文本匹配」，涉及**代码语义理解**，接近独立科研课题；**不要一上来就做全量 OT 算法**。  
- **建议（初期实现）**：**不要自己造轮子**；**初期仅实现基于「上下文锚点 (Context Anchors)」的匹配**：  
  - 在生成 AI 建议时，除 `replacement_text` 与 `range` 外，保存**漏洞代码前后各 N 行**（如 3 行）的文本作为**锚点**。  
  - 应用时：在当前文档中**查找该锚点文本**；若找到唯一匹配，则在该位置应用修改；若找不到或有多处匹配，则**不应用**并提示「文档已变更，请重新获取建议」。  
  - 这样在「用户只做了小幅编辑、锚点仍在」的场景下可成功应用，且实现简单、可验证；**不承诺**变量重命名、跨文件移动等复杂场景。  
- **小结**：TDD 约定初期采用**上下文锚点匹配**，全量 OT / 语义级 Fuzzy Patching 列为后续演进，避免首版陷入算法黑洞。

### 7.4 CLI / 本地接口要点

- 当前版本没有可运行的 FastAPI HTTP Server；对外扫描入口以 CLI、LSP stdio 和 GitHub Actions 集成为准。
- CLI 接收项目路径或增量扫描参数，返回 JSON/HTML/Markdown/SARIF 报告。

## 9. 非功能需求

### 9.1 性能

- **LSP**：单文件分析在常规体量下保持亚秒级响应；大文件可考虑超时或限长。  
- **漏扫**：支持缓存与增量，大项目通过并行与增量控制总时间。  
- **报告生成**：HTML/JSON 等不阻塞扫描主路径，可异步写文件。  

#### 9.1.1 性能与进程模型：Python 天花板与「每次 Spawn」不可接受

- **现实**：当前核心引擎与 LSP 均运行在 **Python** 进程中。Python 的 GIL 与解释器特性使 AST 遍历与图计算在 CPU 密集时较慢；且**每次请求都 spawn 新子进程**在开发机上可能仅 ~100ms，但在企业环境（如 Windows + 杀软对子进程扫描）下常会飙到 **500ms–1s**，导致保存后 IDE 卡顿甚至假死，用户会直接卸载插件。同时，单次 Python 进程启动会加载 20–50MB 内存，多文件同时触发多次 spawn 会瞬间占用数百 MB，不可接受。  
- **结论**：**「每次 Spawn 新进程」不作为可选方案**；TDD 不定义「方案 B：每次请求起新进程」，仅保留下述**单守护进程**架构。

- **定死架构：单守护进程 + 任务队列（Client-Server）**  
  - LSP 进程启动时**同时启动**一个**常驻 Worker 守护进程**（或由扩展侧先于 LSP 启动守护进程）。  
  - 所有扫描请求通过 **IPC**（**Named Pipe** 或 **Local Socket**）投递到该守护进程的**任务队列**，由守护进程执行规则引擎 + 污点分析，结果经同一 IPC 回传 LSP，LSP 再发布 Diagnostic。  
  - LSP 主线程仅做协议与投递，不执行重计算、不阻塞用户输入。  
  - **长期**：**核心计算模块（AST 遍历、污点传播）必须设计为 FFI 友好结构**，为未来用 Rust/Go 替换该模块预留接口；竞品（Ruff、OXC）已用 Rust 达到 10ms 级，Python 即使用守护进程在大型项目上仍可能慢一个数量级。

- **进程生命周期管理**  
  - **守护进程崩溃**：LSP 或扩展侧检测到 IPC 断开/无响应时，应尝试**重启守护进程**并重连；若多次失败则降级为「本次会话不再提供实时扫描」，并提示用户检查环境或重启 IDE。  
  - **僵尸进程**：守护进程退出时须正常关闭 IPC 与子线程，避免僵尸；LSP/扩展在 deactivate 或退出时**主动通知守护进程优雅退出**（如发送 shutdown 消息），并设置 join 超时，超时后必要时 kill。

- **内存保护策略（常驻进程 + 虚拟节点映射的泄漏风险）**  
  - 常驻守护进程内会维护**虚拟节点映射**（见 6.6.2.1）等复杂引用结构；Python GC 对**图/节点/映射**的循环引用未必能及时释放，若用户长时间在 IDE 中编写、守护进程从不重启，内存可能持续增长甚至数小时后占用数 GB 导致卡死。  
  - **必须**在 TDD 中约定**内存保护策略**：  
    - 每处理完 **N 个文件**（如 1000 次扫描）或守护进程**内存占用超过阈值**（如 500MB），守护进程执行**优雅重启**（Graceful Restart）：排空队列、完成当前任务后退出，由 LSP/扩展重新拉起新进程，从而释放内存。  
    - 实现上可对「虚拟节点映射」等大结构按文件或按批做**上限或定期清理**，避免无界增长；具体阈值与 N 可在配置中暴露。  
- **小结**：分析不阻塞 LSP 主线程、**仅采用单守护进程 + IPC + 任务队列**；删除「每次 Spawn」方案；并必须包含**进程生命周期**与**内存保护（上限/优雅重启）**设计。

### 9.2 安全

- 报告与 Web 输出中所有动态内容必须转义（防 XSS）。  
- API Key 仅通过环境变量或安全配置注入，不写入代码与日志。  
- 依赖与传输：使用证书验证，避免禁用 SSL 验证。  
- **源码隐私**：禁止将未脱敏的完整源码写入日志或发送至不可信端点；AI 调用若涉及外部 API，须符合 6.4.1 的隐私与合规约束（最小上下文、用户确认或本地/私有化部署）。  

### 9.3 可维护性与可扩展性

- 规则与 Source/Sink/Sanitizer 配置化，便于新增漏洞类型与语言。  
- 分析引擎与 LSP/API 解耦，便于单测与替换实现。  
- 日志结构化，便于排查与审计。

## 10. 异常流与错误处理

本节描述「当事情出错时」系统的行为与策略。TDD 不仅描述 Happy Path，还应明确各环节的失败模式与应对，避免仅做线性「输入→规则→输出」假设。

### 10.1 AST 解析失败（语法错误等）

- **场景**：用户代码存在语法错误、或当前语言解析器无法识别的构造，导致 AST 解析失败或得到错误树。  
- **策略**：  
  - **不崩溃**：分析入口（如 `analyze_javascript` / `analyze_python`）必须 try/except，解析异常时返回**空 Finding 列表**并打日志（含文件路径与异常类型）。  
  - **降级**：可选策略——若配置允许，AST 解析失败时**降级为正则扫描**（仅运行不依赖 AST 的规则），并在 Finding 或报告中标记「本文件为降级扫描，结果可能不完整」。  
  - **LSP**：单文件解析失败时，对该文档发布**空 Diagnostic 列表**（清空旧诊断），必要时在 statusBar 或 outputChannel 提示「当前文件语法错误，已跳过安全扫描」。  
- **不采用**：直接抛出未捕获异常导致 LSP 进程退出或整次扫描中断。

#### 10.1.1 异常处理的「避重就轻」：Parser 兼容性是核心 KPI

- **现实**：对 SAST 工具而言，**AST 解析失败率**是核心 KPI。若 Parser 对**现代语法**（如 TypeScript 新特性、装饰器、新 JS 语法）支持不足，导致**频繁降级为正则**，则：  
  - 降级后仅能跑简单模式匹配，**漏报率 (False Negative)** 会非常高，大量真实漏洞无法被 AST 规则与污点分析覆盖。  
  - 「降级」不应成为默认兜底而无约束，否则产品在真实项目上会表现很差。  
- **文档必须包含**：**Parser 兼容性测试标准**，而不是轻飘飘一句「降级处理」。例如：  
  - **TypeScript/JavaScript**：Parser（如 Tree-sitter 对应语法）须通过** TypeScript 官方 Test Suite**（或等价标准）的**不低于 95%** 用例，否则视为不达标，需升级 Parser 或语法定义而非依赖降级。  
  - **Python**：可约定通过 CPython `ast` 模块能解析的语法集合为基准，或引用社区标准测试集与通过率阈值。  
- **结论**：在 TDD 中明确「Parser 兼容性达标是发布/验收条件之一」；降级仅为**偶发语法错误**（如用户正在输入未闭合括号）时的容错，**非常规路径**。若某语言长期依赖降级才能扫，则应在路线图中列为「Parser 升级」优先项。

### 10.2 RAG 检索超时或失败

- **场景**：ChromaDB 查询或向量检索超时、服务不可用、或返回异常。  
- **策略**：  
  - **不阻塞用户**：RAG 增强为**可选后置步骤**；若 RAG 超时或失败，**仅跳过 RAG 增强**，仍保留并返回已有 Finding（规则引擎 + 污点结果）。  
  - **超时配置**：RAG 检索须设置超时（如 3–5 秒）；超时后记录日志并继续，不无限等待。  
  - **LSP/IDE**：RAG 若在 LSP 侧被调用（如 Code Action「获取修复建议」），必须**异步**执行；在等待 RAG/LLM 期间**不阻塞**编辑或打字；超时后向用户展示「建议获取失败，请重试或检查网络」。  
- **不采用**：RAG 阻塞主扫描线程或阻塞 LSP 的 didSave/didChange 响应。

### 10.3 AI（LLM）调用失败或超时

- **场景**：外部 LLM API 超时、限流、返回 4xx/5xx、或返回体无法解析。  
- **策略**：  
  - **可选功能**：AI 增强为显式可选；未配置 API Key 或未开启时不调用，不报错。  
  - **超时与重试**：调用前设置超时（如 10–15 秒）；可配置有限次数重试（如 1–2 次），重试间隔使用退避。  
  - **失败时**：不因 AI 失败而丢弃已有 Finding；仅标记「AI 建议不可用」，在报告或 IDE 中可展示「获取 AI 建议失败」。  
  - **Code Action**：若用户点击「应用 AI 建议」时 LLM 失败，展示错误提示，不执行任何编辑。

### 10.4 LSP 与 IDE 侧异常

- **场景**：LSP Server 进程崩溃、客户端断开、或某次请求携带无效参数（如空 URI、无法解析的 path）。  
- **策略**：  
  - **单次请求**：对单文档的扫描异常（如上述 AST 失败）仅影响该文档，不影响其他已打开文档的 Diagnostic。  
  - **进程**：LSP Server 应避免未捕获异常导致进程退出；顶层对请求处理器做 try/except，返回空结果或合规错误响应。  
  - **无效输入**：无法识别语言、或 URI 无法转为合法路径时，发布空 Diagnostic 并打日志，不抛异常。

### 10.5 扫描过程中的文件/项目变更

- **场景**：批量扫描时，文件在扫描过程中被删除或内容被外部修改。  
- **策略**：  
  - **单文件**：读取文件内容时若发生 IO 错误（如文件不存在），跳过该文件并记录，继续其余文件。  
  - **版本**：LSP 侧已在 7.3 约定「发布前校验文档 version」，避免脏数据。  
  - **增量扫描**：若基于 Git diff 的增量扫描在运行中检测到工作区变更（如用户保存了文件），可约定「本次扫描结果仅对扫描开始时的快照有效」，不强制重扫，避免竞态。

### 10.6 错误处理篇幅与优先级

- 异常流设计应占 TDD 的**相当比例**（建议与 Happy Path 的「数据流、模块职责」相当，约 20%–30% 篇幅），便于实现与评审时逐项落实。  
- 实现时每个上述场景都应有对应分支与测试（如「AST 解析失败时返回空列表」「RAG 超时时跳过增强」）。

### 12.3 结论与下一步验证

- **当前文档评估**：在具备工程落地性与逻辑闭环的前提下，可视为**约 85/100**；剩余风险主要来自**性能（Python 固有约束）**与**复杂逻辑的实现细节**（内联坐标映射、AI 建议的锚点/模糊匹配）。  
- **瓶颈在验证**：文档再迭代空间有限，下一步瓶颈在于**用代码验证核心风险**，再推进全面实现。建议在进入大规模开发前完成以下两项 PoC，实验通过后项目可进入实现阶段。  

| PoC | 目的 | 做法 |
|-----|------|------|
| **PoC 1：内联与坐标** | 验证「坐标地狱」与映射表必要性 | 写一个 Python 脚本，用 `ast` 解析两个简单函数，**手动实现一次内联**，并打印内联后 AST 节点的行号。可立即体会虚拟行号与原始源码的错位，以及维护「虚拟节点 → (CallSite, DefinitionSite)」映射的必要性。 |
| **PoC 2：多进程启动延迟** | 验证「实时检测」体验是否成立 | 在 **VS Code 插件环境**下测试 Python `multiprocessing` 的**子进程启动延迟**。若单次启动达 200ms 量级，则「保存后实时出 Diagnostic」的体验会崩，需改为**常驻守护进程**而非每次请求起新进程；PoC 结果应反哺 9.1.1 的架构选型（守护进程 vs 进程池）。 |

- **行动建议**：先完成上述两实验，再据此锁定内联实现方式（含坐标回溯）与 LSP 侧分析架构（多进程 vs 常驻守护）；文档与实现对齐后，项目可成。
